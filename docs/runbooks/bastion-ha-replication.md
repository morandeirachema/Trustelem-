# Runbook: WALLIX Bastion HA Database Replication

Date: 2026-09-23. Source: [Bastion 12.0.2 Deployment Guide](https://marketplace-wallix.s3.amazonaws.com/bastion_12.0.2_en_deployment_guide.pdf)
chapters 2, 4, 5, 6 and 7, plus the [Bastion 12.3.2 Functional Administration Guide](https://pam.wallix.one/documentation/admin-doc/bastion_en_administration_guide.pdf)
and the [Bastion Quick Start](https://marketplace-wallix.s3.amazonaws.com/Bastion-quickstart-en.pdf).
Quotes are verbatim. Items the public guides do not cover are marked "not documented"; they
are expected in the System Operations Guide available to customers on the support portal.

Supporting role in this repository: the Trustelem integration (RADIUS secondary authentication,
SAML domains, mappings) is configuration data, so it replicates between the nodes; the SIEM,
licence, network and SNMP settings do not, and must be set on each node.

## 1. Facts

- "WALLIX Bastion 12 removed the High-Availability File System Replication (DRBD) feature. To
  use High-Availability abilities in your infrastructure, you must use the Database Replication
  feature."
- "an SSH tunnel with port forwarding is established between Bastions to secure communication
  between the databases. This tunnel is managed by the autossh service that keeps the tunnel
  permanently running."
- Slaves (and both masters in Master/Master) "request updates from the Master node using the
  outbound port 3307 (source) and the inbound port 3306 (destination)".
- Modes: Master/Slave(s) ("No modification must be performed by the Slaves") and Master/Master
  ("there is a primary Master and a secondary Master. The primary Master is the Master Bastion
  on which the replication is installed").
- Not replicated: Audit; Session Management > Recording Options; Configuration > Configuration
  Options; Configuration > Connection Messages; Configuration > License; Configuration > Audit
  Logs; System > Network; System > Time Service; System > SNMP; System > SMTP Server; System >
  Service Control; System > SIEM Integration; Users > Accounts: the GPG fingerprint; Targets >
  Devices: the certificates for the device.

Limitations table (verbatim excerpts):

| Feature | Limitation |
|---------|------------|
| Audit | "The audit tables are not replicated ... all Bastions have their own audit session tables." |
| API provisioning | "In Master/Master mode, API provisioning must not be performed simultaneously from both Bastions." |
| Cloning VMs | "Do not clone virtual machines and use them to set the replication. This leads to errors related to the universally unique identifier (uuid)." |
| Passwords | "all password actions must always be performed from the (primary) Master node." |
| Password changes | Master/Master: "only schedule the password change on the primary Master node". |
| Check-in | "In Master/Slaves mode, do not use the Change password at check-in option." |
| Approvals | Master/Master: replicated. Master/Slaves: "approvals must be requested and validated only on the Master." |

## 2. Prerequisites

- "all Bastions used for the replication use the same version of WALLIX Bastion."
- "All Bastions must have the encryption initialized before installing the Replication".
- "The database of the primary Master Bastion will erase the database of other Bastion in the
  replication."
- "FQDN and IPv6 are not supported in the HA feature configuration. You must only use the IPv4
  address for Bastions."
- "WALLIX recommends to configure a SMTP server on the (primary) Master and to synchronize all
  Bastions on the same timezone".
- Configuration file `/etc/sqlreplication`, generated by `--create-conf-file`.
- Interface: since DRBD was removed "the eth1 network interface can now be configured and used
  like any other" interface, and "When the eth1 interface is used for HA database replication,
  the associated administration features must be manually enabled from the System > Service
  control page for replication to work" ([release notes WAB-7947 and WAB-17651](https://pam.wallix.one/documentation/release-notes/bastion-rn-en.html)).
- Both nodes fully initialised (accounts, network, NTP, licence, SIEM, recording storage) as in
  section 3, since those settings do not replicate.

## 3. Node initialisation (both nodes)

Factory state: eth0 `192.168.10.5/24`, SSH administration on 2242, GUI on 443; "RSA private
keys (SSH 2242, HTTPS, and RDP) inserted in WALLIX Bastion must be greater than or equal to
3072bits."

| Account | Role | Factory value |
|---------|------|---------------|
| `admin` | GUI super administrator | admin / admin |
| `wabadmin` | CLI connection user on 2242 | SecureWabAdmin, must be changed |
| `wabsuper` | sudo user (`super`, then `sudo -i`) | set at initialisation |
| `wabupgrade` | upgrades from the CLI | set at initialisation |
| `wabbootadmin` | GRUB user | SecureWABBoot, must be changed |

Privilege escalation used by every procedure:

```
wabadmin$ super
[sudo] password for wabsuper:
wabsuper$ sudo -i
```

First boot wizard (Deployment Guide 4.1): keyboard, new passwords for the four accounts,
hostname, eth0 static address, FQDN. Then (4.2) disk encryption:

```
# on-premises or VM
bastion-luks-update --interactive --change-passphrase
# cloud other than AWS
bastion-luks-update --reencrypt
```

and `WABSecurityLevel` to select "SOG-IS CES 1.3 Agreed Cryptographic Mechanisms up to 2030".
GUI (4.3): change `admin`, initialise encryption (passphrase of at least 12 characters with upper case, lower case, a number and a special
character; "once a passphrase has been set, it cannot be deleted", Quick Start 5.3.2), licence via Configuration > License > Download context file, time service,
a named `product_administrator`, first backup with a backup key of exactly 16 characters (section 4.3 of the guide says "at
least 16", chapters 6 and 7 "must be exactly 16 characters long"; use 16, gap B8),
delete the default `admin`, run `WABChangeDbRootPassword`.

Ports to open between nodes and to the outside are in the architecture report, section 6.3.

## 4. Install Master/Master (Deployment Guide 5.1.1)

On the node that will be the primary master:

```
# bastion-replication --create-conf-file
What kind of SQL replication do you want to implement?
1. Master/Master
2. Master/Slave(s)
Enter the number of your choice: 1
What is the ip address of your Bastion No 1? 10.10.54.44
what is the wabadmin password of your bastion 10.10.54.44?
what is the wabsuper password of your bastion 10.10.54.44?
Do you want to disable the password rotation on the bastion 10.10.54.44? [y/N]N
What is the ip address of your Bastion No 2? 10.10.54.46
what is the wabadmin password of your bastion 10.10.54.46?
what is the wabsuper password of your bastion 10.10.54.46?
Do you want to disable the password rotation on the bastion 10.10.54.46? [Y/n]Y
What is your passphrase? leave blank, if there is none ?
# bastion-replication --prerequisite-check
# bastion-replication --install
# bastion-replication --monitoring
# bastion-replication --install-monitoring      # cron for replication status
# bastion-replication --install-notification    # e-mail when replication is down
```

The rotation prompt defaults differ: keep rotation on node 1, disable it on node 2, which
matches the rule that password operations run only from the primary master.

Master/Slaves (5.1.2) is the same dialogue with choice `2`; step 5.1.2 2c defines the number
of slaves (the example transcript does not show that prompt).

## 5. Command reference (5.2)

```
bastion-replication --create-conf-file | --prerequisite-check | --install | --status
                    | --monitoring | --install-monitoring | --uninstall-monitoring
                    | --install-notification | --uninstall-notification | --notification NOTIFICATION
                    | --resync | --dump-resync | --add-slave | --elevate-master
                    | --stop | --start | --uninstall | --version | --debug
```

- `--resync`: "Resynchronize all slave with the Master".
- `--dump-resync`: "Create a SQL dump (without the auth/session history) send it to Slave node
  and resync the slave with the Master".
- `--elevate-master`: "Elevate a slave bastion from an existing cluster master/slave".
- `--uninstall`: "Uninstall replication on every node, to run on Master".
- Not runnable on a slave in Master/Slave mode: `--resync`, `--dump-resync`,
  `--install-monitoring`, `--install-notification`, `--notification`, `--monitoring`.

Impact (5.2):

| Option | Restarts primary master DB | Restarts slaves / secondary master DB | Erases DB data on all nodes except the primary master |
|--------|:-:|:-:|:-:|
| `--install` | yes | yes | yes |
| `--dump-resync` | no | yes | yes |
| `--resync` | no | yes | no |
| `--uninstall` | yes | yes | no |

## 6. Daily checks

1. `bastion-replication --status` and `--monitoring` on the primary master; both nodes listed
   as in sync.
2. Replication e-mails (installed with `--install-notification`) arriving at the operations
   mailbox.
3. Create a test object (for example a time frame) on the primary master and confirm it on the
   other node within seconds; delete it.
4. `WB_Event=wabaudit` lines in the SIEM from both nodes.

Sample output of `--status`, `--monitoring` and `--prerequisite-check` is not documented
publicly.

## 7. Failover and failback

Master/Master: both nodes accept logins at all times, so a node loss is handled by the front
end (load balancer, DNS or Access Manager cluster). Keep administration, password rotation and
API provisioning on the surviving node only; when the failed node returns, check
`--monitoring` and use `--resync` (or `--dump-resync` if the data diverged) from the primary
master.

Master/Slaves: promote with `bastion-replication --elevate-master` ("Elevate a slave bastion
from an existing cluster master/slave"; *inference:* run on the surviving slave), then repoint
the front end. The step-by-step failover and failback procedure is not documented
publicly; rehearse it on the test cluster and record your own runbook. For restoring backups on
replicated nodes the guide gives, in the major-upgrade context, "stop the HA replication"
(`bastion-replication --stop`), import each backup on its node, then `bastion-replication
--start` (6.2.1 step 9).

Disable the failed node in Access Manager (Bastions page, Active Bastion off) so the cluster
stops trying it ([AM release note WAB-17043](https://pam.wallix.one/documentation/release-notes/am-rn-en.html)).

## 8. Major upgrades in HA mode (chapter 6: to Bastion 12)

Two methods:

- **Controlled deployment** (recommended): build a parallel cluster, restore each node's backup
  with `wallix-config-restore.py --testing-mode -f <BACKUP_FILE>` ("deactivates all interaction
  workflows"), install HA on the parallel master with `bastion-replication`, import
  recordings with `WABSessionLogImport`, test, then freeze the live cluster
  (`systemctl mask --now cron` on each live node), redo backups and recordings, on the parallel
  cluster `bastion-replication --stop`, re-import, `bastion-replication --start`, and finally
  deactivate "Disable password rotation" and "Disable remote trace write" under
  Configuration > Configuration options > Global > Advanced options.
- **Auto-deployment**: same without the testing mode; "All actions during the migration process
  are lost" between backup and promotion.

Backups: System > Backup/Restore with a backup key ("must be exactly 16 characters long" in
chapters 6 and 7); "In case of a Master/Slaves setup, start with the Slaves."

Minor upgrades and hotfixes (chapter 7):

```
ssh -p 2242 wabupgrade@<BASTION_IP_ADDRESS>
BastionSecureUpgrade -i /home/wabupgrade/<ISO>.iso -c /home/wabupgrade/<ISO>.iso.sha256sum -s /home/wabupgrade/<ISO>.iso.sha256sum.sig
```

Verify the ISO signature (Deployment Guide 3.2.1.1.1): `gpg --import <CA>.pub.gpg` and
`gpg --verify <ISO>.iso.sha256sum.sig <ISO>.iso.sha256sum` (signer "WALLIX PAM R&D Team");
optional here, because "the WALLIX upgrade script also verifies the signature" (7.1).
If the upgrade fails, answer `N` to the lockdown deactivation prompt, reboot in rescue mode,
then `/opt/wab/bin/BastionSecureUpgrade --unlock-system`.

Because of WSA-2026-07-0001, any cluster on 12.3.0 to 12.3.6 or 12.4.0 must be taken to
12.3.7 or 12.4.1 and later ([advisories](https://www.wallix.com/support-services/alerts/)).

## 9. Certificates and keys per node

- GUI: replace `ca.crt`, `server.pem`, `server.key` in `/var/wab/apache2/ssl.crt`, then
  `systemctl restart apache2`; self-signed regeneration `WABGuiCertificate selfsign -f`.
- RDP proxy: `rdpcert --key --inkey=./<key>.key --x509 --inx509=./<cert>.pem --force`, then
  `systemctl restart redemption`.
- SSH proxy host keys: `/var/wab/etc/ssh/server_rsa.key`, `/var/wab/etc/ssh/server_ed25519.key`,
  regenerated with `WABSshServerGenRsaKey.sh`.
- Access Manager pins the Bastion certificate and fingerprints: after any change, toggle
  "Reset Bastion Certificate", "Reset SSH Fingerprint" and "Reset RDP Fingerprint" on the AM
  Bastions page.

Source: [Quick Start 5.4](https://marketplace-wallix.s3.amazonaws.com/Bastion-quickstart-en.pdf),
[AM Admin Guide 13](https://pam.wallix.one/documentation/admin-doc/am-admin-guide_en.pdf).

## 10. Services on the appliance

From the disk-expansion procedure (Deployment Guide 3.2.2.2), the services stopped before
resizing `/var/wab` (autossh, used by replication, is not in that list): `wabwatchdog`, `wabrestapi`, `wabgui`,
`redemption` (RDP proxy), `sashimi` (SSH proxy), `wallix-validator`, `superset`,
`wallix-discovery`, `wallixsession`, `wallixcelery`, `wabsystemconfiguration`, `syslog-ng`,
`acpid`, `cron`, `wab-backupdaemon`, `mariadb`. Data lives on LV `vg00/lvwab` mounted at
`/var/wab`. GUI equivalent: System > Service control.

## 11. What replicates from the Trustelem integration

*Inference* from the chapter 5 exclusion list: everything not excluded is configuration data
and replicates.

| Object | Replicated | Action on the second node |
|--------|:-:|---------------------------|
| External authentications (AD, RADIUS to Trustelem Connect, SAML) | yes | none |
| Authentication domains, secondary authentication, mappings | yes | none |
| User groups, profiles, authorizations | yes | none |
| API keys for Access Manager | yes | none |
| SIEM integration, SMTP, SNMP, NTP, network | no | configure on each node |
| Licence | no | one licence file per node |
| Recording options and storage | no | configure on each node |
| Device certificates and GPG fingerprints | no | re-accept on each node; in Master/Master "you must upload the GPG key to both master nodes" (Admin Guide 4.5) |
